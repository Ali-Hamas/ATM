01 — About the Project

What this is, in one paragraph

This is a cardless ATM authentication layer. The customer opens their bank's existing mobile app, taps "Cardless ATM Access," scans a QR code on the ATM screen, and approves with biometrics. The ATM unlocks within a second — ready to dispense cash. No physical card. No PIN typed at the machine. No new app installation.

The key insight. We don't replace the bank's systems. We sit between the existing ATM and the existing mobile banking app and answer exactly one question: "is this person authorised to use this ATM session right now?" Everything else — balances, ledgers, transaction posting, the cash dispenser — stays with the bank.

Why this matters

  • Card skimming dies. No card at the ATM means nothing to clone or photograph.
  • Shoulder-surfing dies. The PIN is never typed on the ATM keypad — auth happens on the customer's phone.
  • No customer onboarding. Customers already trust their bank app. We add one new button inside it.
  • No ATM hardware changes. The ATM just needs a screen that can display a QR and an internet connection.
  • Cards become optional, not removed. Existing card flows keep working. This is a parallel path.

03 — How It Works

The 5-step authentication flow

1

ATM mints a session

Customer taps "Cardless Cash Withdrawal" on the ATM. ATM calls POST /api/session. Backend creates a session in pending state, signs a JWT (HS256) containing the session ID + ATM ID + 60-second expiry, returns the token to the ATM. ATM renders the token as a QR code.

2

ATM subscribes to push updates

ATM opens a WebSocket at /ws?sid=<sessionId>. It will sit there listening, waiting for the backend to tell it "this session was just approved."

3

Customer's phone scans & approves

Customer opens the bank app on their phone, taps "Cardless ATM Access," allows camera, points it at the QR. App reads the JWT (offline — no internet needed for the scan itself). Customer taps "Approve with biometrics." Phone POSTs /api/session/approve with the JWT + device ID + customer reference.

4

Backend validates & pushes

Backend verifies the JWT signature, checks the session is still pending and not expired, mutates state to approved, writes an audit log row, and pushes {type:"approved", session} over the WebSocket to the waiting ATM.

5

ATM unlocks — customer takes cash

ATM screen flips to "Authenticated, Welcome [Name]" (green check animation). Customer picks an amount, ATM dispenses cash, ATM calls /consume. Session moves to consumed. Cannot be replayed.

Total time, real-world. 8–12 seconds from "tap Continue" to "cash dispensed" — faster than inserting a card and typing a PIN.
04 — Step-by-Step Run Guide

How to run the demo on your laptop

Prerequisites (one-time setup)

  • Go 1.22+ — download from https://go.dev/dl/, run installer, reopen terminals.
  • Node.js 20+ — only needed if you want to rebuild the UI or use the mobile app.
  • Expo Go app on your phone — App Store / Play Store. Only needed for the full mobile demo.
  • Same Wi-Fi network for phone + laptop.

Step 1 — Start the server (one terminal)

cd "M:\Banking app\backend-go" go run ./cmd/server

Wait for: auth middleware listening on :4000. Leave it running.

Step 2 — Open the ATM screen

In any browser, visit:

http://localhost:4000

You'll see the DemoBank ATM kiosk. Click Continue → Cardless Cash Withdrawal. A QR code appears inside a gold countdown ring (60 seconds).

That alone proves the system works. The Go backend is serving the ATM screen, the REST API, and the WebSocket — all from one port, one binary.

Step 3 — Prove the API end-to-end (PowerShell)

Open a second PowerShell window. From the repo root, run:

.\test-demo.ps1

You'll see:

=== 1. Creating session === sessionId : 77463772-101a-44d8-9ec1-bfc079fd512b atmId : ATM-DEMO-001 ttl : 60s === 2. Approving session (simulating phone scan) === status : approved customer : Ali Hassan === 3. Audit log === 06:44:26 session.created sid=77463772 06:44:26 session.approved sid=77463772

This is the proof a non-technical viewer (or a bank executive) needs.

Step 4 — Full demo with a real phone (optional, impressive)

  1. Find your laptop's Wi-Fi IP: open a new terminal, run ipconfig, look for the Wi-Fi IPv4 (e.g. 192.168.1.42).
  2. Open mobile-app/App.tsx. Find const API_BASE = "http://10.0.2.2:4000";. Replace the IP with your laptop's Wi-Fi IP. Save.
  3. In a new terminal:
    cd "M:\Banking app\mobile-app" npm install # first time only npx expo start
  4. Open Expo Go on your phone, scan the QR shown in this new terminal. The bank app loads.
  5. On the laptop ATM screen, click through to the QR. On the phone, tap "Cardless ATM Access," scan, approve. Laptop ATM flips to "Authenticated" instantly.

Step 5 — Show the audit log to Sir

While the demo is running, in any browser:

http://localhost:4000/api/audit

Every event with timestamp. This is the compliance hook that banks care about most.

07 — Integration Contract

Where the two halves meet

The simulation track and authenticator track meet at exactly one place: the HTTP + WebSocket contract on localhost:4000. As long as both sides agree on this contract, they can be developed independently.

REST endpoints

MethodPathPurpose
POST/api/sessionATM creates a new pending session, gets a JWT for the QR.
GET/api/session/{id}Anyone reads current session state.
POST/api/session/approveMobile app approves a scanned QR (body: qrToken, deviceId, customerRef).
POST/api/session/{id}/consumeATM marks session done after dispense.
GET/api/auditFull audit log (demo only — production would scope).
GET/api/healthLiveness check + nonce.
WS/ws?sid=<sessionId>ATM subscribes here; receives push when session changes state.

Session state machine

create approve consume [ none ] ─────────────────▶ pending ─────────────────▶ approved ─────────────────▶ consumed │ │ 60s elapses, sweeper ticks └────────────────────────▶ expired

08 — Scope

What's locked, what's deferred

Locked v1 (what we built)

  • QR-based authentication only. One factor, one channel — the customer is on a phone they already trust, approving a session they already understand.
  • Stateless, short-lived tokens. JWT HS256 signed; 60-second TTL; one-shot consume.
  • Audit log for every state change. Compliance-ready trail.
  • WebSocket push to ATM. Sub-second unlock latency.
  • Single-binary deployment. One .exe, no Node, no npm at deploy time.

Deferred to v2+ (what we deliberately did NOT build)

  • OTP / SMS fallback. Phone biometrics are stronger and we don't want to depend on telco delivery.
  • Face recognition / liveness check. Belongs inside the bank app's biometric layer, not the middleware.
  • NFC tap-to-auth. Adds hardware complexity; QR works on every phone made in the last decade.
  • Persistent database. In-memory store with Redis-ready interface. Switch when persistence is needed.
  • mTLS to ATM hardware. Production concern; current demo uses HTTPS as the boundary.
  • Rate limiting / fraud heuristics. Add when a bank pilot is scoped.
Why a small scope is the right scope. Banks adopt new auth layers only when the failure modes are exhaustively understood. A QR-only v1 with one signed token, one TTL, one state machine, one audit table is something a security team can read in an afternoon. Every feature we don't ship in v1 is a feature we don't have to defend in v1.
